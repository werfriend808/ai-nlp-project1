# claim_extractor.py 모델 교체 비교 (HCX-003 → HCX-DASH-002)

- 대상: `agent/preprocessing/claim_extractor.py` (`extract_claims`)
- 결론: **HCX-DASH-002로 교체함** (기본 모델을 `MODEL = "HCX-DASH-002"`로 변경).
- 이유 요약: HCX-003은 긴 기사에서 컨텍스트 길이 초과로 절반이 통째로 실패했고, HCX-DASH-002는
  같은 샘플에서 전부 성공 + 2.6배 빠름 + 품질 대리 지표도 비슷하거나 더 나음.

## 실행 방법

프로젝트 루트에서 실행 (`.env`에 `HCX_API_KEY` 필요, 두 모델 각각 실제 호출):

```
python -m agent.preprocessing.eval_claim_extractor_model
```

## 비교 방법

- `data/data.csv`(관련도 라벨 `True`인 기사)에서 랜덤 8건 샘플링 (seed=42), few-shot 프롬프트에
  이미 쓰인 기사 3건은 제외.
- **주의**: `data.csv`에는 "정답 Claim 리스트"가 없어서(classifier처럼 사람이 매긴 정답 라벨이
  없음) 정밀도(precision)/재현율(recall) 같은 정답 대비 정확도는 잴 수 없음. 대신 자동으로 셀 수
  있는 대리 지표(proxy metric) 4개로 두 모델을 상대 비교함:
  - **형식 파싱 성공률**: JSON 파싱까지 실패 없이 끝났는지 (요청 자체가 거부되는 경우 포함)
  - **응답 시간**: 기사 1건당 `extract_claims()` 호출 소요 시간
  - **추출 claim 수**: 기사당 평균 몇 개를 뽑았는지
  - **수치 포함 비율**: claim.sentence에 숫자가 실제로 있는지 (2단계 정의상 "수치 기반 주장"만
    뽑아야 하므로, 숫자 없는 문장이 섞이면 오탐)
  - **필드 채움 비율**: period/unit/population 3개 필드 중 채워진 비율 (구조화 정보량)
  - **claim_type 유효 비율**: `interfaces.py`의 4종(규모/증감률/비교/전망) 안에 드는 비율 (형식
    지시 준수도)

## 결과 (n=8개 기사, 모델당 8회 호출, 2026-07-24 실행)

| 지표 | HCX-003 | HCX-DASH-002 |
|---|---|---|
| 형식 파싱 성공 | **4/8건 (50%)** | **8/8건 (100%)** |
| 평균 응답 시간 | 6.83초 | **2.59초** (2.6배 빠름) |
| 기사당 평균 claim 수 | 2.25개 (성공한 4건 기준) | 1.50개 |
| 수치 포함 비율 | 45.8% | **62.5%** |
| 필드 채움 비율 | 52.8% | 50.0% |
| claim_type 유효 비율 | 83.3% | 87.5% |

### 실패 4건의 원인 (전부 HCX-003만 실패)
```
400 {"status":{"code":"40003","message":"Context length exceeded. Adjust the input length
or reduce the value of max tokens parameter"},"result":null}
```
실패한 4건 모두 기사 본문이 길어서(prompt 조립 후 약 15,000~19,000자) HCX-003(v1 엔드포인트,
이전 세대 모델)의 컨텍스트 길이 한도를 넘음. HCX-DASH-002(v3 엔드포인트)는 같은 기사에서 전부
성공 — 컨텍스트 윈도우 자체가 더 넓은 것으로 보임.

## 해석 / 트레이드오프

- **신뢰성·속도는 HCX-DASH-002가 명확히 우세**: 실기사는 길이가 들쭉날쭉한데 HCX-003은 그중
  절반을 컨텍스트 길이 문제로 통째로 못 돌림 — 파이프라인 안정성 관점에서 치명적. 응답 시간도
  2.6배 빠름 (배치 처리량에 직접 영향).
- **품질 지표는 열세가 아님**: 수치 포함 비율(62.5% vs 45.8%)과 claim_type 유효 비율(87.5% vs
  83.3%) 모두 HCX-DASH-002가 오히려 높음 — "가벼운 모델이라 품질이 떨어진다"는 우려와 반대.
- **주의할 점 — claim 수가 더 적음(1.50 vs 2.25개/기사)**: 이게 "불필요한 문장을 덜 뽑아서"인지
  (수치 포함 비율이 더 높은 것과 일치하는 해석) "실제 유효한 주장을 놓쳐서"(재현율 저하)인지는
  이 대리 지표만으로는 구분 불가 — 정답 라벨이 없기 때문. 배치 실행 결과를 몇 건 사람이 직접
  읽어보고 놓친 주장이 있는지 확인하는 게 좋음 (아래 "커버 안 된 것" 참고).
- 순수 API 요금 비교는 하지 않음(콘솔에 요금 정보 접근 권한 없음) — 다만 HCX-DASH-002가
  "경량/저비용" 모델로 안내되는 게 일반적이라, 속도 우세와 함께 비용도 낮을 가능성이 높음.

## 커버 안 된 것 (다음에 필요하면 추가)
- claim 수 감소가 재현율 저하 때문인지 사람이 직접 원문 대조로 확인 안 함 — 정답 라벨(gold
  claims) 세트가 없어서. 필요하면 소수 기사에 대해 사람이 직접 "정답 claim 리스트"를 만들어서
  precision/recall을 제대로 재는 게 다음 단계로 좋음.
- 요금(비용) 자체는 수치로 못 재서 응답 시간으로만 간접 비교함.
- 샘플 8건은 전부 `data.csv`의 True 라벨 기사 중 무작위 추출이라, 특정 분야(경제/금융 기사가
  많이 뽑힘)에 쏠렸을 수 있음 — 다른 분야(고용/인구/부동산 등) 기사로 추가 검증은 안 함.
