# 8단계(explainer.py) 설명 품질 채점 리포트

- 대상: `agent/explain/explainer.py`의 `explain()` — 판정(7단계)이 끝난 Claim/TableCandidate/
  ComputedResult/Verdict를 받아 사람이 읽을 자연어 설명(explanation_text/limitation)을 생성
- 평가 샘플 41건: explainer.py self-test 3건 + judge 골든셋(`verify_judge_on_golden.py`)이
  실제로 judge()를 통과시킨 26건 + 오늘 세션에서 7단계까지 도달했던 실제 기사 재실행 12건
- 채점 방식: **자동 스크립트 없이, 41건 explanation_text를 하나하나 직접 읽고** 아래 5개 항목을
  O/X로 채점 (샘플 수가 적어 자동화 대신 수동 채점 — 사람이 직접 근거통계/계산방식/판정이유/한계/
  숫자 정확성을 원본(computed, verdict.reason)과 대조)
- **최종 결론: 5번(정확성/환각 없음)이 가장 약한 항목이었고, 원인은 explainer_prompt.txt에
  "주어진 숫자를 그대로 인용하라"는 규칙이 없어서 모델이 스스로 재계산·단위환산·연도추정·항목합산을
  하다가 틀리는 것. 4라운드에 걸쳐 프롬프트 규칙을 추가하고 temperature=0.0을 적용했지만
  85.4%(v1) → 68.3%(v2, 악화) → 80.5%(v3, 회복) → 78.0%(v4, 소폭 재악화)로, 원래 수준(v1)을
  아직 회복하지 못했다. temperature=0.0에서도 동일 입력에 매 라운드 다른 오류가 나타나는 것으로
  보아 **API 자체의 잔여 비결정성 + 프롬프트 규칙만으로는 못 막는 근본적인 패턴(자체 재계산,
  시점 추정, 하위 항목 합산)** 이 남아있다고 결론.**
- **실전 파이프라인 검증 추가**: `batch_runner.py`로 실제 기사를 1~8단계까지 돌려서 그 순간
  진짜 나온 judge() 출력으로 explain()을 16건 실호출 — `ExplainerError` 0건, 숫자 정확성
  15/16(93.8%). 다만 표본이 작고 우연히 쉬운 유형(기간 불일치)에 몰려있어 "실전에서는 문제없다"로
  일반화할 근거는 아님 — 자세한 내용은 "실전 파이프라인 검증" 절 참고.

## 채점 항목

1. **근거통계** — 어떤 통계표가 근거인지 명시했는가
2. **계산방식** — 원자료를 어떻게 가공했는지 설명했는가
3. **판정이유** — 왜 이 판정이 나왔는지 설명했는가
4. **한계** — 판정의 한계를 얼버무리지 않고 구체적으로 적었는가 (limitation 필드가 null이면 무조건 X)
5. **정확성** — explanation_text의 숫자가 실제 computed.raw_value/verdict.reason과 일치하는가(환각 없는가)

## 방법론 메모

- 41건의 입력(Claim.sentence, TableCandidate.table_name/source_meta, ComputedResult, Verdict)을
  1차 수집 시점에 JSON으로 고정(freeze)해두고, 프롬프트를 바꿀 때마다 **완전히 동일한 입력**으로
  `explain()`만 다시 호출해서 순수하게 프롬프트/설정 차이만 비교했다. TableCandidate.source_meta는
  원본 실행 값을 저장해두지 않아 `table_catalog.json`에서 title로 재조회해 근사 복원했다 — 극소수
  케이스(C05/C11)에서 리랭커가 원래 골랐던 표 설명과 다른 문구가 나올 수 있음(예: "SITC 무역통계").
  이건 채점 항목 1(근거통계)에는 영향 없음(어차피 통계표를 명시는 함).
- `agent/preprocessing/hcx_client.py`의 `call_hcx` 기본 `temperature=0.2`이고, 원래
  `explain()`은 이를 덮어쓰지 않아 **결정적이지 않은 호출**이었다. v2(1차 수정) 재채점에서
  오히려 정확성이 나빠지는 역설적인 결과가 나온 데에는 이 비결정성이 섞여 있었을 가능성이 있어,
  v3부터 `explain()`에 `temperature: float = 0.0` 기본값을 추가했다. 다만 **v3→v4 비교는 둘 다
  temperature=0.0인데도 결과가 달라져서, temperature=0이라도 HCX API 자체의 잔여 비결정성이
  있다는 게 실측으로 확인됐다** — 이후 라운드 비교는 "프롬프트만의 순수 효과"로 단정하지 말고
  노이즈가 섞인 값으로 해석해야 함.

## 실전 파이프라인 검증 (frozen 재구성이 아닌, 그 순간 실제로 나온 judge() 출력으로 확인)

지금까지의 v1~v4는 41건의 입력을 JSON으로 고정(freeze)해두고 explain()만 반복 호출한
테스트라, "실제 1~8단계가 그 순간 만들어낸 진짜 Claim/TableCandidate/ComputedResult/Verdict"로
검증한 적은 없었다. `agent/pipeline/batch_runner.py`(v4 프롬프트 + temperature=0.0 적용된
`explain()`을 그대로 사용)로 `data_set.csv`의 실제 기사를 1~8단계 전체로 돌려서 확인했다.

**사전에 발견한 버그**: `batch_runner.py`의 `--csv` 옵션이 애초에 동작하지 않고 있었다.
`DATA_CSV_PATH`가 존재하지 않는 `data.csv`를 가리키고 있었다(코드 주석은 "data_set.csv를
data.csv로 고쳤다"고 돼 있었는데 실제로는 반대 — `data_set.csv`가 진짜 파일명이고 `data.csv`는
없음). 실행하면 무조건 `FileNotFoundError`. `data_set.csv`로 수정해서 지금은 정상 동작한다.

**실행**: (1) `--csv` 모드로 25건 무작위 샘플 — 3~4단계에서 대부분 걸러져 explain() 호출 1건만
확보. (2) 표본을 늘리려고 "정부기관 키워드+수치 패턴" 필터로 후보를 추려 14건을 추가 시도 —
explain() 호출 15건 확보(성공 15, 실패 0). 총 **explain() 실호출 16건**.

### 결과

- **ExplainerError 발생: 0건 / 16건.** JSON 파싱 실패, "판단불가인데 limitation 누락" 방어
  로직 발동 둘 다 한 번도 안 걸림.
- **정확성**: 16건 중 15건은 explanation_text의 숫자가 computed/verdict.reason과 완전히
  일치(재계산이 필요했던 케이스도 정확 — 예: "19.1%와 4.7% 차이는 14.4%p", "차이가 3.40개월").
  **1건만 경미한 이슈**: "고용노동부... 지난해 월평균 임금" 케이스에서 "지난해(2022년 추정)"라고
  씀 — 확정 서술이 아니라 "추정"으로 명시적으로 헤지했고 computed.period가 정확한 연도를
  못박지 않는 애매한 상황이라 명백한 오류로 보긴 어렵지만, "상대시점 임의 확정 금지" 규칙의
  정신에는 살짝 어긋남.

### frozen 테스트(78.0%, v4)와의 괴리를 어떻게 볼 것인가

실전 표본의 정확도(15/16 ≈ 93.8%)가 frozen 테스트보다 훨씬 높게 나왔다. 다만 이걸 "실전에서는
문제없다"로 성급히 일반화하면 안 된다:

- 표본이 16건으로 작아서 우연의 영향이 크다(frozen 41건 기준 78%면 16건 중 3~4건은 실패가
  나와도 정상 범위).
- 이번 실전 표본은 우연히 대부분 "기간 불일치"(월별 vs 연간) 패턴에 몰려 있었다 — 모델이 이미
  잘 처리하는 유형이다. frozen 테스트에서 실제로 틀렸던 유형(큰 금액 단위환산, 여러 하위 항목을
  기사에서 뽑아 합산, "몇 월"처럼 구체적 시점을 스스로 확정)이 이번 실전 표본엔 우연히 거의
  없었다. 즉 "실전에서 더 잘한다"기보다는 "이번에 걸린 케이스들이 상대적으로 쉬운 유형이었다"에
  가깝다.
- 결론: 남은 취약 패턴(단위환산/하위항목 합산/시점 확정)에 정확히 해당하는 케이스가 실전에서도
  나오면 frozen 테스트와 비슷한 실패율을 보일 것으로 예상해야 한다. "실전 검증 통과"로 결론짓지
  말고, 리뷰 큐(사람 검토)에서 특히 저 세 패턴이 나오는 explanation은 우선순위 있게 볼 것.

## 다음에 필요하면 추가할 것

- **프롬프트만으로는 한계**로 보인다. 특히 C10(하위 항목 합산 금지)처럼 이번 라운드에 정확히
  겨냥한 규칙을 넣었는데도 재현된 사례가 나왔으므로, 다음 단계는 프롬프트 대신 **코드 레벨 가드**를
  고려할 만하다 — 예: `explain()` 응답을 받은 뒤 explanation_text에서 숫자를 정규식으로 뽑아
  `computed.raw_value`/`verdict.reason`에 있는 숫자 집합과 비교해서, 없는 숫자가 나오면
  `ExplainerError`로 재시도시키는 후처리 검증기.
- temperature=0.0이어도 v3→v4 사이에 결과가 흔들리는 걸 실측했으므로, 프롬프트를 더 다듬을
  계획이라면 **같은 41건을 여러 번(예: 3회) 반복 실행**해서 라운드별 순수 효과와 노이즈를
  분리해야 신뢰할 수 있는 비교가 된다. 지금까지의 v1~v4는 전부 "1회 실행" 비교라 통계적으로 약하다.
- 이번 41건(frozen)과 16건(실전)은 전부 판정까지 도달한 "성공" 경로만 다룸 — `judge()` 호출
  자체가 실패하는 경로의 품질은 별도 확인 필요.
- 실전 검증 표본(16건)을 더 늘려서 단위환산/하위항목 합산/시점확정이 실제로 걸리는 케이스를
  더 많이 확보하면, frozen 테스트 결과와 더 공정하게 비교할 수 있다.
