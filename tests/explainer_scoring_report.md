# 8단계(explainer.py) 설명 품질 채점 리포트

- 대상: `agent/explain/explainer.py`의 `explain()` — 판정(7단계)이 끝난 Claim/TableCandidate/
  ComputedResult/Verdict를 받아 사람이 읽을 자연어 설명(explanation_text/limitation)을 생성
- 평가 샘플 41건: explainer.py self-test 3건 + judge 골든셋(`verify_judge_on_golden.py`)이
  실제로 judge()를 통과시킨 26건 + 오늘 세션에서 7단계까지 도달했던 실제 기사 재실행 12건
- 채점 방식: **자동 스크립트 없이, 41건 explanation_text를 하나하나 직접 읽고** 아래 5개 항목을
  O/X로 채점 (샘플 수가 적어 자동화 대신 수동 채점 — 사람이 직접 근거통계/계산방식/판정이유/한계/
  숫자 정확성을 원본(computed, verdict.reason)과 대조)
- **최종 결론: 5번(정확성/환각 없음)이 가장 약한 항목이었고, 원인은 explainer_prompt.txt에
  "주어진 숫자를 그대로 인용하라"는 규칙이 없어서 모델이 스스로 재계산·단위환산·연도추정을
  하다가 틀리는 것 — 프롬프트 수정 2라운드 + temperature=0.0 적용으로 85.4%→68.3%(1차, 악화)→
  80.5%(2차, 회복)까지 개선했으나 원래 수준(85.4%)은 아직 완전히 회복하지 못함.**

## 채점 항목

1. **근거통계** — 어떤 통계표가 근거인지 명시했는가
2. **계산방식** — 원자료를 어떻게 가공했는지 설명했는가
3. **판정이유** — 왜 이 판정이 나왔는지 설명했는가
4. **한계** — 판정의 한계를 얼버무리지 않고 구체적으로 적었는가 (limitation 필드가 null이면 무조건 X)
5. **정확성** — explanation_text의 숫자가 실제 computed.raw_value/verdict.reason과 일치하는가(환각 없는가)

## 방법론 메모

- 41건의 입력(Claim.sentence, TableCandidate.table_name/source_meta, ComputedResult, Verdict)을
  1차 수집 시점에 JSON으로 고정(freeze)해두고, 프롬프트를 바꿀 때마다 **완전히 동일한 입력**으로
  `explain()`만 다시 호출해서 순수하게 프롬프트/설정 차이만 비교했다. TableCandidate.source_meta는
  원본 실행 값을 저장해두지 않아 `table_catalog.json`에서 title로 재조회해 근사 복원했다 — 극소수
  케이스(C05/C11)에서 리랭커가 원래 골랐던 표 설명과 다른 문구가 나올 수 있음(예: "SITC 무역통계").
  이건 채점 항목 1(근거통계)에는 영향 없음(어차피 통계표를 명시는 함).
- `agent/preprocessing/hcx_client.py`의 `call_hcx` 기본 `temperature=0.2`이고, 원래
  `explain()`은 이를 덮어쓰지 않아 **결정적이지 않은 호출**이었다. 1차 프롬프트 수정 후 재채점에서
  오히려 정확성이 나빠지는 역설적인 결과가 나온 데에는 이 비결정성이 섞여 있었을 가능성이 있다.
  2차 수정에서 `explain()`에 `temperature: float = 0.0` 기본값을 추가해 이후 평가는 재현 가능하게
  만들었다.

**v2에서 왜 나빠졌는가**: 원래 6건의 오류 중 4건(단위환산 오류 2건, 없는 사실 지어낸 것 1건,
산술 오류 1건)은 실제로 고쳐졌다. 그런데 "확실하지 않으면 지어내지 마라"는 규칙이 역설적으로
모델을 더 적극적으로 만들어서, "작년"/"지난달" 같은 상대시점을 **틀린 특정 연도로 못박는** 새로운
오류가 9건 생겼다(순수 노이즈만으로 보기엔 실패 유형이 한 방향으로 몰려있어 규칙의 부작용으로 판단).

**v3에서 무엇이 회복됐는가**: 상대시점 임의 확정 금지 규칙 + temperature=0.0을 추가하자, v2에서
새로 생긴 9건 중 5건(B-A004-01, B-A024-03, C07, C08, C12)이 다시 고쳐졌다. 다만 4건
(B-A024-01, B-A025-02, B-A038-03, C10)은 v3에서도 여전히 남아있고, v3에서 새로 2건
(B-A027-03, B-A032-02 — 검증 안 된 부가 주장을 확인된 사실처럼 서술)이 재발했다.

## 다음에 필요하면 추가할 것

- 3라운드 프롬프트 수정을 한다면 남은 두 패턴을 직접 겨냥: (a) "직접 덧셈/뺄셈/단위환산이 필요하면
  실행하지 말고 그 사실 자체를 한계로 적어라", (b) "verdict_reason에 있는 비교 대상 숫자만 쓰고,
  기사 문장에 있는 다른 하위 항목 숫자를 합산·재조합하지 마라".
- 이번 41건은 전부 판정까지 도달한 "성공" 경로만 다룸 — `judge()` 호출 자체가 실패하거나
  `ExplainerError`(판단불가인데 limitation 누락)가 발생하는 실패 경로의 품질은 별도 확인 필요.
- N=41 단일 실행 비교라 통계적으로 약함. 프롬프트를 더 다듬을 계획이라면 같은 41건을 여러 번
  반복 실행해서(temperature=0이라도 API 자체의 미세한 비결정성은 남을 수 있음) 신뢰구간을 보는 게
  더 안전하다.
