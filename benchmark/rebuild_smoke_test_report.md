## 2. 영문 표 처리 기준

**기존 코드에 이미 명확한 판별 기준이 존재함을 확인**(임의로 새로 만들지 않고 그대로 재사용):

- `VW_CD == "MT_ETITLE"` — 원본 크롤링에서 "영문KOSIS" 뷰로 수집된 표를 표시하는 필드(이미 있음, `crawl_table_catalog.py`/`prepare_vdb_export.py`에 기록됨)
- `_looks_english(text)`(`agent/kosis/patch_english_table_names.py:52`) — 표 이름에 알파벳이 하나라도 있고 전부 ASCII면 영문으로 판정하는 함수(이미 있음, 실사용 이력 있음)

**실측 결과** (`tables.jsonl` 287,498건 전수):
- `VW_CD == 'MT_ETITLE'`: 2,827건
- `_looks_english(TBL_NM)`로 판별된 영문 표: 2,832건 (전체의 0.99%)
- 두 기준은 거의 일치(2,827 vs 2,832, 차이 5건은 MT_ETITLE이 아니면서 영문으로 남은 예외 케이스로 추정)

**production 검색 코드(`agent/mapping/*.py`)에서 VW_CD/영문 필터를 실제로 사용한 흔적은 없음**(grep 0건) — 즉 현재 production은 영문 표를 별도로 걸러내지 않고 그대로 검색 대상에 포함하고 있다.

**결론(사용자 지시 그대로 보고)**: "영문 표는 이번 20건 테스트 대상에서 제외했으나(기존 `_looks_english`/`VW_CD` 기준 사용), 전체 재구축에서 영구 제외할지는 별도 결정이 필요하다." — 임의로 제외 정책을 만들지 않았음.

⚠️ 표본 편향 주의: 이번 20건은 "균등 간격 샘플링"으로 뽑았는데 결과적으로 item/axis/value 개수가 적은 지자체 소규모 표 위주로 뽑혔다(값 개수 최대 66개, 셀 분할이 필요한 초대형 표는 표본에 없었음). 실제 279,305건에는 셀 40,000개 초과로 기간을 여러 번 쪼개 재요청해야 하는 대형/밀집 표도 섞여 있어, 위 추정치는 **낙관적 하한**일 가능성이 높다. 규모/복잡도를 층화한 표본(예: item/axis 개수 상위 표 포함)으로 재측정하는 것을 권장.

## 14. 2-worker 병렬화 결과

실측(동일 서버, 동일 API 키 1개, 20건씩, 서로 다른 표 사용):

| worker 수 | 처리시간(20건) | 처리율 |
|---|---|---|
| 1 | 108초 | 0.185건/초 |
| 2 | 36초 | 0.556건/초 |

**→ 2-worker가 1-worker 대비 약 3배 빠름(실측 확인).** KOSIS API의 분당 200건 한도는 코드에서 스레드 간 공유되는 단일 `MinIntervalRateLimiter`(0.32초 간격)로 강제되므로, 이론상으로는 동시성이 늘어도 호출 "속도" 자체는 늘지 않아야 하는데도 실측 3배 향상이 나온 이유는 — 한 스레드가 API 응답(네트워크 왕복)을 기다리는 동안 다른 스레드가 그 시간을 겹쳐 쓸 수 있기 때문(레이트리밋 게이트 자체는 직렬이지만, 게이트+왕복 지연이 스레드 간에 오버랩됨). rate limit 위반(err=40)은 이번 실행 로그에서 관측되지 않음, 중복 처리된 table_id도 0건(PK 제약으로 구조적 보장).

## 15. 4-worker 운영 가능 여부 판정

**검증 불가 / 위험 요소 발견 — 이번 테스트로는 승인할 수 없음.**

이유(코드 실측 근거):
- `reembed_worker.py`의 레이트리미터(`MinIntervalRateLimiter`)는 **API 키 단위**로 공유된다(`_rate_limiters` dict, 키 문자열이 dict key). 즉 "worker"란 실제로는 하나의 프로세스 안 스레드(concurrency)일 뿐, 서로 다른 API 키를 쓰지 않으면 진짜 독립적인 처리량 증가가 아니다.
- 사용자가 그린 구조("SERVER A: Worker1+Worker2, SERVER B: Worker1+Worker2" = 4 worker)를 4개의 독립된 처리량으로 만들려면 **서로 다른 API 키가 4개** 필요하다. 그런데 `.env`에는 `KOSIS_API_KEY`, `KOSIS_API_KEY_2` **2개만** 존재한다.
- 만약 SERVER_A와 SERVER_B가 같은 키를 동시에 재사용하면(예: 둘 다 KOSIS_API_KEY 사용), KOSIS의 "분당 200건" 한도는 **키 기준으로 KOSIS 서버 측에서 집계**되므로(코드 주석에 명시된 실측 사실), 두 서버가 동시에 같은 키를 쓰면 합쳐서 200건/분을 초과해 오히려 err=40(rate limit) 재시도가 늘어나 처리량이 떨어질 위험이 있다 — 이번 20건 테스트는 7-1 단독 실행이라 이 충돌 시나리오 자체를 검증하지 못했다.

**따라서 검증된 것은 "서버 1대 + API 키 1개 + 2-worker(스레드)"까지다.** 이 구성을 그대로 서버 2대로 확장(서버당 키 1개씩, 총 2개 키, 2개의 독립된 처리량)하는 것은 안전하다고 판단하지만, 문자 그대로의 "4-worker(서버당 2개, 총 4개)"는 **API 키가 2개뿐인 이상 검증도, 승인도 할 수 없다.**

## 16. 발견된 문제

1. **이전 ETA(10~15시간)가 실측 대비 크게 낙관적**(위 13절) — 재구축 계획에 즉시 반영 필요.
2. **"4-worker" 구조가 현재 보유한 API 키 개수(2개)로는 문자 그대로 구현 불가** — 서버당 별도 키가 있어야 안전하게 확장 가능.
3. 이번 20건이 전부 `status=success`로 성공해서 **`error_no_data`/`error_other`/재시도(backoff) 경로가 한 번도 실행되지 않았다** — 실패/재시도 처리 로직 자체는 코드 리뷰로만 확인했고, 실제 실패 사례로 검증하지는 못했다.
4. 표본이 소규모 지자체 표 위주로 뽑혀 **셀 분할([31] 40,000셀 초과)이 필요한 대형 표가 표본에 없었다** — 대형 표 처리 시간/안정성은 이번 테스트로 확인되지 않음.
5. `org_whitelist.json`의 `org_id=739` 기관명이 부자연스러움("전남광주통합특별시 고흥군") — 기존 데이터 품질 이슈, 이번 테스트가 만든 문제 아니며 수정도 하지 않음(범위 밖).
6. GPU VRAM 실시간 피크를 계측하지 못함(모니터링 미병행) — OOM 0건이라는 간접 증거만 있음.
